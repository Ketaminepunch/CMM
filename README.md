# Call me maybe - Function Calling via Constrained Decoding

## Description

This project turns a small, unreliable local LLM (`Qwen/Qwen3-0.6B`, 0.6B
parameters) into a function-calling engine that is **100% reliable by
construction**, not by hoping the model behaves.

Given a natural-language prompt and a catalog of available functions (name,
parameters, types, description), the program picks the right function and
extracts correctly-typed arguments, e.g.:

```
"What is the sum of 40 and 2?"
  -> {"name": "fn_add_numbers", "parameters": {"a": 40, "b": 2}}
```

Small models are notoriously bad at spontaneously producing valid JSON
often succeeding well under half the time when just prompted for it. Instead
of prompting-and-hoping (explicitly forbidden by the subject), this project
implements **constrained decoding from scratch**: at every generation step,
the model's logits are masked so only tokens that keep the output both
syntactically valid JSON *and* compliant with the function's schema can ever
be chosen. Invalid output is structurally impossible, not just unlikely.

## Algorithm Explanation

The model never generates a raw JSON string and gets parsed afterwards 
generation *is* the parser. The output shape
`{"name": "<fn>", "parameters": {...}}` is built token by token, and at each
point in that structure only the model is asked for a decision when there
actually is one to make.

1. **Structural JSON is never generated by the model.** Braces, key names,
   quotes and separators are known in advance, encoded with the SDK's
   tokenizer, and appended directly to the token stream zero forward
   passes spent on structure the grammar already knows.

2. **Closed choices use a token-id `Trie`** (`src/grammar/tries.py`). Every
   function name and `true`/`false` is inserted into a trie over token-id
   sequences. At each step, only the children of the current trie node are
   left unmasked in the logits, so a hallucinated function name is not just
   unlikely - it is not a legal token sequence at all. Once the name
   completes, the pipeline commits to that function's parameter schema for
   the rest of generation.

3. **Open values use per-type finite state machines**
   (`src/grammar/fsm.py`), built over precomputed token-id sets
   (`src/grammar/token_sets.py`) derived once from the vocabulary file:
   - `NumberFSM` implements `-?digits(.digits)?`. Since a number has no
     closing delimiter, the terminator token (`,` or `}`) is folded into the
     FSM's own alphabet and chosen by the model itself.
   - `StringFSM` covers the string body: any token whose decoded bytes
     contain no unescaped `"`, no bare `\`, and no control byte is legal;
     after a configurable cap (40 tokens) the closing quote becomes the only
     legal choice, so a string can never run forever.

   Every state only unmasks tokens that are valid *in full* - a token can
   never straddle a grammar-state boundary, so there is no
   character-vs-token mismatch to reconcile.

4. **Masking is applied with `numpy`**: legal token ids keep their logit,
   everything else is set to `-inf`, and the next token is the `argmax` of
   the masked array (`masked_argmax`, `src/decoding/primitives.py`). Decoding
   stops when the JSON structure is syntactically complete  the model's own
   EOS token is never relied on, so validity is structural, not
   probabilistic.

The generation pipeline itself follows the standard LLM loop described in
the subject (prompt -> tokenize -> input ids -> logits -> next-token
selection, repeated per token), with step 6 (token selection) replaced by
masked selection over the grammar's legal set instead of unconstrained
argmax/sampling.

## Design Decisions

- **Token-granular grammar, not character-granular.** Walking a
  character-level pushdown automaton against tokens that may be several
  characters long invites boundary mismatches. Instead, every FSM/trie state
  only ever unmasks whole tokens that are valid in that state, so tokenizer
  merges never break the grammar.

- **Token healing at every text/model seam.** The biggest practical lesson
  of this project (see `FIXES.md`, not part of the graded deliverable) is
  that a model only behaves sensibly when the context in front of it looks
  like real tokenized text. Forcing an "unnatural" boundary  e.g. writing a
  bare `"` where training text almost always has `",` or `"}` merged 
  makes the model's next-token ranking effectively noise. Both string
  opening and closing are therefore handled by letting the model *choose*
  the merged quote token itself (`quote_openers` / `quote_starts` in
  `TokenSets`), rather than force-writing a plain quote and hoping the model
  continues sensibly afterward.

- **Single combined prompt preamble** (`src/prompts.py`), built once per run
  from the loaded function catalog, rather than re-prompting per parameter.
  It lists every function's name/parameters/description dynamically (never
  hardcoded to the example schema, since the grader uses different
  functions) plus a small set of few-shot examples chosen to cover the
  hardest observed cases  escaped quotes, backslashes, multi-string-
  parameter calls  since the model only reliably reproduces patterns it has
  actually been shown.

- **Types come from the schema, never from the generated text.** Whether a
  parameter is emitted as Python `int` or `float` is decided by the
  function's declared `"integer"`/`"number"` type in
  `functions_definition.json`, not by whether the model happened to type a
  decimal point.

- **Pydantic for all data crossing a boundary**: the function catalog, the
  prompt list, and the result objects are all validated `pydantic` models
  (`src/models.py`), so malformed input files fail with a clear validation
  error instead of an unhandled exception deep in the decoder.

- **`llm_sdk` is treated as a black box**: only its public methods
  (`encode`, `get_logits_from_input_ids`, `get_path_to_vocab_file`) are
  used; no private attributes or methods.

## Performance Analysis

- **Accuracy**: 100% correct function selection and argument extraction on
  the full test suite (11/11), including edge cases: floats, negative
  numbers, multi-parameter functions, quoted strings, Windows paths with
  backslashes, and escaped quotes inside strings.
- **Validity**: 100% of output is syntactically valid JSON that matches the
  requested schema exactly, by construction  invalid tokens are never
  reachable, so there is nothing to retry or repair.
- **Speed**: `get_logits_from_input_ids` reprocesses the full sequence on
  every call (no KV-cache), so the main cost is the number of forward
  passes. This is kept low by never spending a forward pass on structural
  tokens (braces, keys, separators are appended directly), by choosing
  string closers greedily via token healing instead of burning the full
  40-token cap, and by building the model, vocabulary and grammar exactly
  once per run and reusing them across every prompt. The full example suite
  completes well within the subject's 5-minute budget.
- **Reliability**: malformed or missing input files are caught at load time
  with a clear message instead of crashing; a single prompt that hits the
  token cap raises `TooManyTokens`, which is caught per-prompt so one bad
  case cannot take down the whole run.

## Challenges Faced

Most failures during development were the same root cause wearing different
clothes: **a hand-written token boundary that the model had never seen in
training makes its next-token ranking meaningless**, even though the
grammar itself was correct. A few concrete examples:

- **Fake string closers.** With only the bare `"` token allowed to close a
  string, the model's actual favorite closing tokens (`","`, `"}`, merged
  with neighbors) were banned, so it substituted a legal look-alike (a curly
  `"`) and kept dictating, leaking prompt text into the value. Fixed by
  treating *any* token that starts with the `"` byte as a valid closer, and
  rewriting the token stream to a bare quote afterward so later context
  stays clean.
- **No way to write `\` or `"` inside a string** produced silently wrong
  output (`C:/Users/...` instead of `C:\Users\...`) or repetition loops when
  the model wanted to write an escape it wasn't allowed to. Fixed by
  admitting exactly the two escapes the data needs (`\"`, `\\`) and
  unescaping the result with `json.loads`.
- **Lost leading characters on string open** (e.g. a path's leading `/`)
  because forcing a bare opening quote put the model in a context it had
  never seen before a path. Fixed by letting the model choose the opening
  quote token itself from a precomputed set of quote-leading, body-safe
  tokens, and prepending whatever payload trails the quote to the value.
- **Integers coming back as floats** turned out not to be a decoding bug at
  all  `gen_number` already produced the right Python type, but the
  `pydantic` result model's type union was missing `int`, so validation
  silently coerced every integer back to a float.

## Testing Strategy

- **Grammar-level unit tests** (`test_decoder.py`) exercise `NumberFSM`,
  `StringFSM` and the tries against fake logits, with no model download
  required  sanity-checking digit/string-body set sizes, minus/dot
  guards, the string length cap, and the trie shape.
- **End-to-end smoke test** (`test_end_to_end.py`) drives the real
  `src/prompts.py` + `decode_function_call` pipeline against
  `Qwen/Qwen3-0.6B` and the subject's example data, and independently
  re-parses the raw generated text with `json.loads` to confirm it matches
  the `(name, params)` the decoder returned  a second, independent check
  that the constrained output really is valid JSON.
- Both scripts are dev-only sanity checks (per the subject, not submitted
  or graded) and are excluded from lint/type-checking.
- Manually stress-tested beyond the committed examples with ambiguous
  prompts, negative numbers, large floats, strings containing apostrophes
  and escaped quotes, and Windows-style paths with backslashes.
- Deliberately corrupted/removed input files to confirm the program reports
  a clear error instead of crashing.
